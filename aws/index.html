myapp.com on AWS: EKS edition

A full-stack web + mobile platform with messaging, a media pipeline, AI/ML and analytics. The web and app tiers run as pods on Amazon EKS instead of EC2 Auto Scaling groups.

Hover over a node to trace its flows. Solid = synchronous, dashed = async / batch.

1 How it flows

  1. Request path: users (browser / mobile) → Route 53 (myapp.com) → Application Load Balancer (created by the AWS Load Balancer Controller from a Kubernetes Ingress) → web pods → API pods. Both tiers spread across AZs.
  2. State: API pods use ElastiCache (cache), RDS Multi-AZ (transactions), DynamoDB (sessions, carts) and Neptune (graph-based recommendations).
  3. Async: API pods publish to SNS (push / fan-out), send email via SES, and queue jobs in SQS. KEDA scales worker pods on queue depth.
  4. Media:
    • The browser uploads straight to S3 with a presigned URL issued by the web tier.
    • An S3 event triggers Lambda → Rekognition (labels / moderation) and MediaConvert (video transcode) → S3 media bucket.
    • CloudFront edge locations serve the media to web and mobile users.
  5. AI / ML: SageMaker trains on the data lake and deploys a custom model to a SageMaker endpoint, which the API pods call. Amazon Bedrock adds GenAI features (search, chat).
  6. Analytics: API pods stream events to Kinesis → S3 data lake → EMR (Spark) → Redshift → QuickSight dashboards. Glue catalogs the lake and runs ETL from DynamoDB and RDS.

Architectural Service Directory

The AWS services behind the secure, 3-tier e-commerce design. The workload and requirements are the same as the Azure version.

CF

CloudFront + AWS WAF

Global entry point with CDN caching, WAF managed rules and Bot Control. Reaches private origins through VPC origins.

SH

AWS Shield Advanced

Managed DDoS protection with the Shield Response Team and cost protection. Optional; decide on cost.

ALB

Internal Application Load Balancer

Private L7 router behind CloudFront. Sends pages to the frontend pods and /api to the private API Gateway.

AG

API Gateway (private REST)

Cognito JWT authorizer, throttling, usage plans and webhook validation. Reachable only through the execute-api VPC endpoint.

CG

Amazon Cognito

Customer identity: user pools, managed login, MFA and threat protection. Issues the JWTs that API Gateway validates.

EK1

Frontend EKS

Presentation tier: server-rendered web UI and backend-for-frontend APIs.

EK2

Middle Layer EKS

Business logic: order workflow, Equifax verification and payment orchestration.

EK3

Data Layer EKS

The only tier allowed to read or write the data stores. Owns the transactional outbox.

VL

Amazon VPC Lattice

Service-to-service networking between the clusters. IAM auth policies decide which tier may call which.

SQ

SNS FIFO + SQS FIFO

Ordered, de-duplicated events with fan-out and dead-letter queues. Accessed through VPC endpoints.

NF

AWS Network Firewall

Central inspection and egress VPC: domain allowlist, IPS, and static NAT Gateway Elastic IPs for partners to allowlist.

TGW

Transit Gateway

Hub router connecting workload, shared-services and inspection VPCs, plus on-prem via Direct Connect or VPN.

EQ

Equifax

External identity and credit verification. Called over mTLS from the middle tier through the egress VPC.

PS

Payment Provider (PSP)

Hosted payment fields tokenize cards in the browser, so card numbers never reach AWS.

AU

Aurora PostgreSQL

System of record for orders, payment references, inventory and customers. Multi-AZ, Global Database for DR, accessed through RDS Proxy.

DD

Amazon DynamoDB

Low-latency catalog and durable carts. On-demand capacity; global tables replicate to the DR Region.

EC

ElastiCache for Valkey

Session store and read-through cache. Multi-AZ, TLS and IAM auth. Holds no data that can't be rebuilt.

S3

Amazon S3

Product images and static assets, served only through CloudFront Origin Access Control. Replicated to the DR Region.

KM

Secrets Manager, KMS, ACM

Rotated secrets, customer-managed (multi-Region) keys, and public and private certificates (ACM + AWS Private CA).

CI

GitHub Actions / CodePipeline

CI and Terraform pipelines (one platform to be chosen). OIDC to IAM roles and private runners in the VPC, so no stored keys.

JF

JFrog Artifactory

Build-time registry and Xray scanning, reached over AWS PrivateLink. Promotes signed images to ECR.

ECR

Amazon ECR

Runtime registry: private, replicated to DR, scanned by Inspector. EKS pulls through VPC endpoints.

AR

Argo CD (GitOps)

Pulls approved manifests into each private cluster, so CI never needs access to the EKS API.

CW

CloudWatch & Container Insights

Always-on baseline: metrics, logs, node and pod CPU/memory, alarms, synthetic canaries.

PG

Managed Prometheus & Grafana

Option A metrics and dashboards. Agentless managed scrapers for EKS; Grafana with SSO.

XR

X-Ray / Application Signals

Option A APM: OpenTelemetry (ADOT) traces, service map, SLOs.

DD

Datadog

Option B for APM, dashboards and tracing, instead of the AWS-native APM stack.

SP

Splunk

SIEM. CloudWatch Logs reach it through Amazon Data Firehose; CloudTrail through the S3/SQS input. No forwarder VMs needed.

GD

GuardDuty, Security Hub, Inspector

Threat detection (including EKS runtime), posture checks against PCI and AWS best practices, and vulnerability scanning.

4 DNS

  • Interface endpoints: "private DNS" enabled, so SDKs resolve sqs.us-east-1.amazonaws.com and similar names to private IPs without code changes.
  • Private hosted zone internal.example.com: api.internal.example.com (API Gateway private custom domain) and internal service names.
  • Route 53 Profiles (Network account) share private hosted zones, Resolver rules and DNS Firewall rules with every VPC in every account.
  • Hybrid resolution: Route 53 Resolver inbound/outbound endpoints for on-prem (and Azure/GCP during migrations).
  • Route 53 Resolver DNS Firewall: block known-malicious domains and limit DNS exfiltration.
  • Optional: centralize interface endpoints in the shared-services VPC to save per-AZ endpoint cost at scale.

5 Request Flow & TLS

  1. DNS: www.example.com is a Route 53 alias to the CloudFront distribution.
  2. CloudFront:
    • Terminates TLS (ACM certificate in us-east-1) and applies AWS WAF.
    • /static/* and /images/* go to S3 via Origin Access Control and are cached.
    • /* goes to the internal ALB through the VPC origin.
  3. Internal ALB: HTTPS listener (regional ACM cert).
    • /api/* and /webhooks/* → target group of the execute-api endpoint IPs → private API Gateway.
    • /* → frontend web pods (IP targets via TargetGroupBinding).
  4. API Gateway (private REST): Cognito authorizer, throttling and usage plans, PSP webhook signature check. Forwards over a VPC Link to the frontend cluster's internal NLB.
  5. Frontend → Middle → Data: calls go through VPC Lattice services. The auth policy allows only the calling tier's Pod Identity role (SigV4).
  6. Data → stores: Aurora through RDS Proxy (IAM auth token); DynamoDB, SQS and Secrets Manager through VPC endpoints with IAM.
  7. Middle → Equifax / PSP: TGW → Network Firewall (domain allowlist) → NAT Gateway Elastic IPs, with an mTLS client certificate from Secrets Manager.

6 Edge & Gateway Configuration

CloudFront + AWS WAF + Shield

  • Origins and caching: origin groups for reads; cache policies for static assets, no caching for dynamic paths. HTTPS only, TLS 1.2+.
  • WAF web ACL (scope CLOUDFRONT):
    • Core rule set, Known bad inputs, SQLi, IP reputation.
    • Bot Control.
    • Account Takeover Prevention on /login.
    • Rate-based rules on /login, /checkout and /api/*; geo-match if US-only.
  • Shield Advanced: decide on cost (monthly subscription). Adds the response team, cost protection and automatic L7 mitigation. TBD
  • Central management: Firewall Manager applies WAF policies across accounts.

Internal ALB

  • Placement: internal scheme in the alb subnets (3 AZs), registered as a CloudFront VPC origin.
  • Security group: allows only the CloudFront VPC-origins service security group.
  • Listener and targets: HTTPS with an ACM cert, path rules from §5, deletion protection. The frontend target group is bound to pods by the AWS Load Balancer Controller (TargetGroupBinding).
  • Logs: access logs to the Log Archive S3 bucket.

API Gateway (private REST API)

  • Access control: the resource policy allows only the workload VPC endpoint. A private custom domain api.internal.example.com carries its own ACM cert.
  • Cognito authorizer: checks issuer, audience/scope and expiry.
  • Throttling: stage and method throttling, plus usage plans for partner APIs.
  • Request handling: request validation (JSON schema) and header mapping, removing internal headers.
  • Webhooks: /webhooks/psp is validated (HMAC signature in a Lambda authorizer) before it's forwarded.
  • Backend: integration over a VPC Link to the frontend internal NLB, with TLS to the backend.
  • Logs: access logs to CloudWatch with no request bodies; X-Ray tracing on.

Equifax and payments

  • Equifax:
    • mTLS client cert and OAuth credentials in Secrets Manager.
    • 3 s timeout, retries with jitter for idempotent calls, circuit breaker.

12 Identity, Secrets & Certificates

  • Customers: Cognito user pool with managed login, MFA for sensitive changes and threat protection (adaptive auth). Authorization-code flow with PKCE.
  • Workforce:
    • IAM Identity Center federated to the corporate IdP (Entra ID / Okta) with SCIM; permission sets per role.
    • No IAM users.
    • Root user: MFA plus centralized root management; break-glass procedure.
  • Workloads: EKS Pod Identity, one role per service:
    • Frontend: invoke the Lattice middle service.
    • Middle: invoke Lattice data; publish to SNS; read the Equifax/PSP secrets.
    • Data: rds-db:connect to RDS Proxy; DynamoDB tables; SQS consume; KMS decrypt on its keys.
  • CI: GitHub OIDC (token.actions.githubusercontent.com) or CodeBuild service roles. Trust conditions pin repo:<org>/<repo>:environment:prod.
  • Secrets: Secrets Manager with rotation, mounted through the Secrets Store CSI driver (AWS provider). Never in Git or image layers.
  • Certificates: ACM public certs (auto-renew; CloudFront certs in us-east-1). AWS Private CA for internal TLS through cert-manager. Alert on expiry through EventBridge.

13 Security & Compliance Controls

  • SCPs (what principals may do):
    • Deny leaving the organization.
    • Deny disabling CloudTrail, GuardDuty or Config.
    • Restrict Regions.
    • Deny creating IAM users and access keys.
  • RCPs (resource control policies): an organization-wide data perimeter, so resources can't be accessed by identities outside the org.
  • Detection:
    • Security Hub (FSBP, CIS, PCI DSS v4 standards).
    • GuardDuty, including EKS audit logs, runtime monitoring, S3, RDS and malware protection.
    • Inspector (ECR, EC2, Lambda).
    • Macie for PII in S3.
    • IAM Access Analyzer (external and unused access).
    • Config conformance packs; Detective.
  • Encryption: KMS CMKs for PII stores, TLS everywhere, aws:SecureTransport conditions, S3 account-level Block Public Access.
  • Evidence: CloudTrail organization trail in Log Archive (S3 Object Lock); AWS Audit Manager for PCI evidence.
  • Before go-live: threat model, penetration test (within AWS's policy), PCI SAQ A validation.

D Hands-on AWS Experience: Architect / DevOps (30)

These are the questions interviewers use to tell real production experience from certification knowledge. Each sample answer is written the way a strong candidate talks: first person, specific, with numbers, commands and what went wrong.

Use these as a pattern, not a script. Replace the stories with your own. Interviewers drill into details ("what was the error message?", "how long did it take?"), and a borrowed story falls apart within two follow-ups. If you haven't done something, say so and explain how you would do it.
H1A pod in a private subnet calls an external API. Walk me through the packet path. Where have you seen it break?
Networking
What they're checking: whether you understand SNAT, route tables, NAT, DNS, and have debugged it for real.

"The pod resolves the hostname through CoreDNS, which forwards to the VPC resolver at the .2 address. Leaving the VPC, the packet is SNAT'd to the node's IP. The subnet route table sends 0.0.0.0/0 to the NAT Gateway in that AZ, then the internet gateway.

I've seen it break in three ways:

  • One NAT Gateway for all AZs. When that AZ had issues, every AZ lost egress, and we were also paying cross-AZ charges. We moved to one NAT per AZ.
  • DNS throttling. CoreDNS hit the resolver's limit of about 1,024 packets per second per ENI during a traffic spike. We saw intermittent i/o timeout on lookups and fixed it with NodeLocal DNSCache.
  • NAT port exhaustion. Too many connections to one partner endpoint. The CloudWatch metric ErrorPortAllocation went up. We fixed connection reuse in the client and added secondary IPs to the NAT Gateway.

To debug, I start with VPC Flow Logs and Reachability Analyzer."

Likely follow-up: "How do you prove it's DNS and not the network?"
Red flag: describing NAT without knowing it's per-AZ or that it charges per GB.
H2Security group vs NACL: when did you actually use a NACL?
Networking
What they're checking: stateful vs stateless in practice, not the textbook table.

"Security groups are my main control. They're stateful, allow-only, and I reference other SGs instead of CIDRs, so rules survive IP changes.

I've used NACLs twice:

  • During an incident, to deny an abusive IP range quickly. Security groups can't express deny rules.
  • As a guardrail, so data subnets can never talk to public subnets, even if someone misconfigures an SG.

The lesson I learned the hard way: NACLs are stateless. The first time, I didn't allow ephemeral ports 1024–65535 outbound. Return traffic was dropped, and we got intermittent timeouts that looked like an application bug."

Likely follow-up: "What are the SG limits per ENI?" (5 SGs per ENI and 60 rules per SG by default; both adjustable.)
H3You need to connect 50 VPCs across many accounts. Peering, Transit Gateway or PrivateLink?
Networking
What they're checking: trade-offs at scale, including cost.
  • Peering is non-transitive and turns into a mesh fast. I'd only use it for 2–3 VPCs, or for a specific high-volume flow.
  • Transit Gateway is my answer at 50 VPCs. It's shared through RAM from a network account, with separate route tables for prod, non-prod and shared services, and an inspection VPC for egress.
  • PrivateLink is for exposing one service to many consumers, especially when their CIDRs overlap.

"We used VPC IPAM to stop CIDR overlap in the first place. One cost win: a database replication flow moved about 40 TB a month through the TGW. We put that one flow on a peering connection and cut TGW processing charges noticeably."

Likely follow-up: "When would you use Cloud WAN or VPC Lattice instead?"
H4An app in VPC A can't reach RDS in VPC B over Transit Gateway. How do you troubleshoot?
Networking
What they're checking: a systematic method, and knowledge of TGW-specific gotchas.

"First I run Reachability Analyzer from the app ENI to the RDS ENI. It usually names the blocking component. Then I check, in order:

  • Subnet route tables on both sides point the other CIDR at the TGW. People often forget the return route.
  • TGW route tables: both attachments are associated, and routes propagate both ways.
  • A TGW attachment subnet in every AZ. We once had resources in AZ-c with no attachment subnet there, and only that AZ failed.
  • RDS security group: allows the source CIDR. Historically you couldn't reference SGs across a TGW; newer TGW supports it within a Region.
  • NACLs, then DNS, to confirm the RDS endpoint resolves to the private IP."
Red flag: jumping straight to "open the security group to 0.0.0.0/0".
H5How do you plan IP addressing for EKS so you don't run out of IPs?
Networking
What they're checking: whether you've hit the VPC CNI IP-exhaustion problem.

"With the VPC CNI, every pod gets a VPC IP, and warm ENIs reserve extra IPs. Our first cluster used /24 subnets and ran out at about 40 nodes. aws-node logged failed to assign an IP address to container and pods sat in ContainerCreating.

What fixed it:

  • Prefix delegation, so each ENI slot hands out a /28, plus a higher max-pods setting.
  • Custom networking on a secondary 100.64.0.0/16 CIDR for pods.
  • Tuning WARM_IP_TARGET and MINIMUM_IP_TARGET.

One surprise: prefix delegation failed with InsufficientCidrBlocks because the subnet was fragmented. We added a subnet CIDR reservation for prefixes. IPv6 is the long-term fix."

H6How does a pod get S3 access without keys? Explain what happens under the hood.
IAM & security
What they're checking: IRSA / Pod Identity mechanics, plus awareness of node-role theft.

"We use EKS Pod Identity. You associate an IAM role with a namespace and service account. The Pod Identity Agent on each node serves credentials on a link-local address. The SDK picks them up automatically; behind the scenes it's an AssumeRoleForPodIdentity call, and the role trusts pods.eks.amazonaws.com.

Before that we used IRSA: a projected service-account token exchanged through STS AssumeRoleWithWebIdentity, with the trust policy pinned on sub = system:serviceaccount:ns:sa.

Two lessons:

  • An early trust policy used a wildcard sub, so any service account could assume the role. IAM Access Analyzer caught it.
  • We set the IMDSv2 hop limit to 1, so pods can't fall back to the node's instance role."
Likely follow-up: "Why move from IRSA to Pod Identity?" (No per-cluster OIDC provider in every trust policy; roles are reusable across clusters; session tags for ABAC.)
H7A role has s3:* allowed but still gets AccessDenied. Why?
IAM & security
What they're checking: the full IAM evaluation chain, and how you debug it.

"An explicit deny anywhere wins, so I walk the chain:

  • SCPs and RCPs.
  • Permission boundary on the role; session policy.
  • Bucket policy, e.g. a deny when aws:SecureTransport or aws:SourceVpce doesn't match.
  • VPC endpoint policy.
  • KMS key policy: the number-one cause for us. The bucket used SSE-KMS and the role had no kms:Decrypt.

To debug, I find the CloudTrail event with errorCode: AccessDenied. The newer error messages also name the policy type that denied. Then I reproduce with the IAM policy simulator."

H8How does your CI pipeline deploy into 10 AWS accounts securely?
IAM & security
What they're checking: no long-lived keys, plus proper cross-account role chaining.

"GitHub Actions authenticates with OIDC to a role in a tooling account. The trust condition pins repo:org/infra:environment:prod. From there it assumes a deploy role in each target account, which trusts only that tooling role, with an aws:PrincipalOrgID condition.

  • Separate plan (read-only) and apply roles.
  • Roles that CI creates get a permission boundary.
  • SCPs stop anyone, including CI, from disabling CloudTrail.

Why I care: at a previous company, Jenkins used IAM user access keys, and one key was printed into a build log. We rotated every key in an afternoon, then moved everything to OIDC within a sprint."

H9How do you manage secrets for apps on EKS, including rotation?
IAM & security
What they're checking: whether rotation actually works end-to-end, not just storage.
  • Source of truth: Secrets Manager.
  • Delivery to pods: External Secrets Operator syncs into Kubernetes Secrets, with Reloader restarting deployments on change. For a few apps we use the Secrets Store CSI driver instead.
  • etcd: envelope-encrypted with a KMS key.
  • Access: each app reads only its own secrets through its Pod Identity role; CloudTrail logs every GetSecretValue.

"The incident that taught me rotation: we turned on RDS password rotation, and an app's connection pool kept the old password. When the old version expired, new connections failed. We moved that app behind RDS Proxy with IAM auth, so the app never sees the password at all."

H10GuardDuty flags crypto-mining on an EKS node. Walk me through your response.
IAM & security
What they're checking: incident-response order: contain before cleaning, and preserve evidence.
  1. Contain without destroying evidence. Cordon the node; swap its security group for a quarantine SG with no inbound or outbound rules; don't terminate it.
  2. Preserve. Snapshot the EBS volumes, save the pod spec, image digest and logs.
  3. Kill credentials. Revoke active sessions for the node and pod roles: a deny policy conditioned on aws:TokenIssueTime, which is what "Revoke sessions" does.
  4. Find the entry point. In our case: a public, unauthenticated dashboard plus a privileged container.
  5. Eradicate. Replace the node (immutable), patch the image.
  6. Prevent. Admission policy blocking privileged pods; GuardDuty Runtime Monitoring; Inspector scan gates in CI.
Red flag: "I'd terminate the instance immediately". That destroys the forensic evidence.
H11How do you upgrade EKS with zero downtime? What went wrong last time?
EKS & Kubernetes
What they're checking: that you have actually done upgrades, not just read the docs.

"One minor version at a time, every quarter, so we never pay for extended support. The order:

  1. Check: EKS upgrade insights, and kubent/pluto for deprecated APIs in manifests and Helm release secrets.
  2. Non-prod first for a week.
  3. Control plane.
  4. Add-ons: VPC CNI, CoreDNS, kube-proxy, at versions compatible with the new release.
  5. Nodes: Karpenter drift replaces them, or a managed node group rolling update.

Two things that bit us:

  • A PDB with maxUnavailable: 0 blocked node drains for hours.
  • On the 1.25 upgrade, a Helm release still referenced PodSecurityPolicy, so helm upgrade failed. We fixed it with the mapkubeapis plugin."
H12Pods are stuck in Pending. How do you debug?
EKS & Kubernetes
What they're checking: a fast, ordered triage.

"I start with kubectl describe pod and read the events:

  • Insufficient CPU or memory: are requests inflated? Is Karpenter scaling? I check its logs for NodePool limits or InsufficientInstanceCapacity.
  • Taints, affinity or topology spread that can't be satisfied.
  • PVC not bound.
  • No IPs left (see aws-node logs).

Real one: a StatefulSet pod rescheduled after a node failure, but its EBS volume was in AZ-a and only AZ-b had capacity. It stayed Pending with a volume node-affinity conflict. We fixed it with volumeBindingMode: WaitForFirstConsumer and enough capacity in each AZ."

H13Production pods are OOMKilled or in CrashLoopBackOff. What do you do?
EKS & Kubernetes
What they're checking: probe design and memory limits from real experience.

"kubectl describe shows Last State: OOMKilled, exit 137. Then I compare the limit with actual usage in Container Insights.

  • Java services: the heap must fit inside the container limit. Use -XX:MaxRAMPercentage=75, not a fixed -Xmx.
  • Memory requests: set requests equal to limits for predictable behaviour.

For CrashLoopBackOff, I read kubectl logs --previous first.

Worst one I've had: the liveness probe called an endpoint that checked the database. During an RDS failover of about 60 seconds, every pod failed liveness and restarted at the same moment, which turned a short blip into a 10-minute outage. Now liveness only checks the process; dependency checks go in readiness; slow starters get a startupProbe."

H14HPA, Cluster Autoscaler, Karpenter: how do you autoscale on EKS?
EKS & Kubernetes
What they're checking: pod scaling vs node scaling, and Spot handling.
  • HPA scales pods on CPU or custom metrics. KEDA scales SQS workers on queue depth.
  • Karpenter launches right-sized nodes directly. It's faster than Cluster Autoscaler, which has to grow an ASG.
  • Spot: we run stateless workloads there with 15+ instance types, and Karpenter handles interruptions through an SQS queue.

"Lesson: Karpenter consolidation was too aggressive at peak and kept moving pods. We added disruption budgets with a schedule (no consolidation 9–18), and karpenter.sh/do-not-disrupt on long batch jobs."

H15How do you expose services on EKS? What does the AWS Load Balancer Controller do?
EKS & Kubernetes
What they're checking: ingress mechanics and load-balancer lifecycle risk.

"The controller turns an Ingress into an ALB, and a Service of type LoadBalancer into an NLB.

  • Target type ip sends traffic straight to pod IPs; instance goes through NodePorts.
  • Subnets are discovered by tags.
  • IngressGroup lets several Ingresses share one ALB, which saves cost.
  • Pod readiness gates stop rollouts from sending traffic to targets that aren't registered yet.

Incident: someone deleted an Ingress during a cleanup. The controller deleted the ALB, and the Route 53 alias went dead. Now internet-facing ALBs are owned by Terraform, and Kubernetes only attaches pods with TargetGroupBinding."

H16How do you deploy to EKS, and how do you roll back?
EKS & Kubernetes
What they're checking: GitOps maturity and safe releases.
  • Argo CD with ApplicationSets per environment; Helm charts with per-environment values.
  • Images pinned by digest.
  • Argo Rollouts canary: 10% → 50% → 100%, with automated analysis on 5xx rate and p99 latency.
  • Rollback: abort the rollout (instant), then git revert, because Git is the source of truth.

"Story: someone hot-fixed prod with kubectl edit during an incident, and Argo self-heal reverted it two minutes later. We kept self-heal on, but documented a break-glass procedure: pause auto-sync on that one app and record it in the incident."

H17How do you structure Terraform across many accounts and environments? How do you handle state?
CI/CD & Terraform
What they're checking: blast radius, state hygiene, team workflow.
  • Modules: versioned in a private registry.
  • "Live" repo laid out as account / region / component (network, data, eks, apps), so each state is small.
  • Backend: S3 with versioning and KMS, using S3-native locking (use_lockfile). Before Terraform 1.10 we used a DynamoDB lock table.
  • Workflow: plan on PR, apply after approval, through OIDC roles. A nightly plan detects drift.

"Why the split: we once had one giant state that took 15 minutes to plan. A stuck lock blocked a production hotfix for 40 minutes. Now components share outputs through SSM parameters instead of one huge state."

H18Terraform plans to destroy and recreate your production database. What do you do?
CI/CD & Terraform
What they're checking: calm, safe state surgery.

"Stop. Don't apply. Find the attribute marked forces replacement. Then:

  • A refactor changed the resource address → add a moved {} block. That was our case after reorganising modules.
  • An attribute managed outside Terraform → lifecycle { ignore_changes }.
  • A real change (e.g. identifier or subnet group) → plan a migration: snapshot, restore, cutover.

Guardrails that should already be there: prevent_destroy, RDS deletion_protection, and a manual snapshot before any risky apply."

H19Design a CI/CD pipeline for a microservice, from commit to production.
CI/CD & Terraform
What they're checking: security gates, progressive delivery, database changes.
  • PR: lint, unit tests, SAST, image build, vulnerability scan (Trivy / Inspector).
  • Merge: push to ECR with an immutable SHA tag, sign the image, bump dev in the GitOps repo, run integration tests.
  • Promotion: stage → prod with an approval gate, then canary with automatic rollback on alarms.
  • Tracking: DORA metrics. We went from weekly releases to about 15 deploys a day.

"The lesson: a migration dropped a column while old pods were still serving, and those pods errored for 5 minutes. Now all schema changes are expand → migrate → contract across separate releases."

H20How do you prevent and detect manual console changes (drift)?
CI/CD & Terraform
What they're checking: governance that still allows emergencies.
  • Prevent: prod permission sets are read-only for humans. A break-glass role exists, and using it triggers an alert.
  • Detect: nightly terraform plan with drift reported to Slack; AWS Config rules.
  • Alert: an EventBridge rule on CloudTrail write events made by human SSO sessions in prod.

"The point isn't zero console use. Every manual change is visible, and gets back-ported to code within 24 hours."

H21Production latency spiked at 2 a.m. Walk me through how you investigated.

Q33Gateway endpoints, interface endpoints (PrivateLink) and NAT: when do you use each?

Q34Why Transit Gateway with a centralized inspection VPC, instead of NAT per VPC?

  • Appliance mode on the TGW attachment keeps flows symmetric across AZs.
  • Trade-offs: TGW data-processing cost, and an extra hop.
  • Alternatives: AWS Cloud WAN for large global networks; VPC Lattice for service-to-service traffic.

Q37SCPs, RCPs, permission boundaries and IAM policies: what does each do?

Q40Scenario: the app is slower on AWS than it was before. How do you troubleshoot?
Post-migration
  1. Compare with the baseline and find the slow hop with X-Ray / Application Signals or Datadog traces.
  2. Leftover cross-cloud or cross-Region calls to a database still at the source.
  3. Burstable instances: T-family instances out of CPU credits.
  4. EBS limits: gp3 baseline IOPS/throughput, or instance EBS bandwidth caps. Raise provisioned IOPS or throughput, or change instance type.
  5. Network: ENA enabled, placement groups, inter-AZ hops.
  6. NAT and DNS: NAT port allocation errors; DNS resolution going back on-prem.
  7. Database: RDS instance class or connection limits (RDS Proxy helps). Use Performance Insights / Database Insights.
  8. Fix, measure, compare again.

Answering tips

  • Structure: context → options → decision → trade-off → validation.
  • AWS interviews often probe the Well-Architected pillars: operational excellence, security, reliability, performance, cost, sustainability. Tie answers to them.
  • Use numbers: TB, Gbps, RTO/RPO, per-GB costs.
  • Amazon-style behavioural rounds use the Leadership Principles. Prepare STAR stories (customer obsession, ownership, dive deep, bias for action).
  • Be honest about hands-on experience versus design knowledge.

Questions to ask the interviewer

  • What's driving the move to AWS, and is there a MAP agreement?
  • Source mix (Azure, GCP, VMware, physical) and number of workloads?
  • Is Control Tower / the landing zone already in place?
  • Target mix of rehost vs modernize?
  • Which compliance regimes apply?
  • Partner involvement and team structure?
  • How is success measured in the first 6 months?
