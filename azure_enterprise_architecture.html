FD

Azure Front Door Premium

Global entry point with WAF, bot protection and CDN caching. Reaches private origins over Private Link.

Internal-mode API gateway: JWT validation, rate limits, quotas and payment webhook verification.

AK2

AK3

The only tier allowed to read or write the data stores. Owns the transactional outbox.

Event backbone with sessions, dead-lettering and duplicate detection. Reached over a Private Endpoint.

FW

Azure Firewall Premium

Hub egress point: FQDN allowlist, IDPS and static outbound IPs via NAT Gateway.

EQ

Equifax

External identity and credit verification. Called over mTLS from the middle tier through the firewall.

PS

Payment Provider (PSP)

Hosted payment fields tokenize cards in the browser, so card numbers never reach Azure.

SQL

Azure SQL

System of record for orders, payment references, inventory and customers. Zone-redundant with a failover group.

DB

Azure Cosmos DB

Low-latency product catalog and durable shopping carts, replicated to the DR region.

RD

Azure Managed Redis

In-memory session store and read-through cache. Holds no data that can't be rebuilt.

BL

Product images and static web assets, served and cached by Front Door over Private Link.

KV

Certificates, secrets and customer-managed encryption keys. RBAC-only, with purge protection.

CI and Terraform pipelines (one platform to be chosen). Both run agents in the hub VNet and authenticate to Azure with federated identity, so no secrets are stored.

5 Request Flow & TLS

  1. DNS: www.contoso.com is a CNAME to the Front Door endpoint (*.azurefd.net). Domain ownership is validated with a TXT record.
  2. Front Door Premium:
    • Terminates public TLS (minimum 1.2) and applies the WAF.
    • /static/* and /images/* go to Blob Storage and are cached.
    • /* goes to App Gateway over Private Link, with no caching.
  3. App Gateway (private): re-encrypts traffic and routes by path:
    • /api/* and /webhooks/* → APIM
    • /* (HTML pages) → the Frontend cluster's internal ingress gateway
  4. APIM: validates the customer JWT (Entra External ID), enforces rate limits and quotas, verifies PSP webhook signatures, strips internal headers and forwards to the Frontend BFF using mTLS.
  5. Frontend → Middle: HTTPS/gRPC to the middle cluster's internal ingress IP. The caller attaches an Entra workload-identity token, and the middle tier validates its audience.
  6. Middle → Data: same pattern, to the data cluster's internal ingress IP.
  7. Data → stores: through Private Endpoints using Entra tokens. No connection strings or keys exist.
  8. Middle → Equifax / PSP: UDR → hub Firewall (FQDN allowlist) → NAT Gateway static public IPs, using an mTLS client certificate from Key Vault.
  9. Async: the Middle and Data tiers exchange events over Service Bus (§11). The Frontend never publishes directly.

6 Edge & Gateway Configuration

Azure Front Door Premium

  • Domain: custom domain with a managed certificate, HTTP → HTTPS redirect, minimum TLS 1.2.
  • WAF policy in Prevention mode:
    • Default Rule Set 2.1 and Bot Manager rule set.
    • Rate-limit rules on /login, /checkout and /api/*.
    • Geo-filter if the store is US-only.
  • Origin groups: priority 1 is the primary-region App Gateway; priority 2 is the DR App Gateway. Health probe on /healthz.
  • Private Link connections: approve them on App Gateway and Storage as a pipeline step, not by hand.
  • Logs: access and WAF logs go to Splunk (§14).

Application Gateway v2

  • SKU: Standard_v2, because the WAF already runs at the edge. Switch to WAF_v2 if the PCI assessor wants an inner WAF.
  • Scale and zones: autoscale min 2 / max 10, zones 1-3.
  • Private-only: private-only deployment (no public IP), with the Private Link configuration in snet-appgw-pl.
  • Listener certificate: loaded from Key Vault by a user-assigned managed identity.
  • Backends: path rules from §5, end-to-end TLS, custom health probes for each backend pool.

API Management

  • Deployment: Premium tier, 2 units across zones, internal VNet mode in its own dedicated snet-apim.
  • Custom domains: gateway, portal and management, all on internal.contoso.com, with certificates from Key Vault.
  • Policies:
    • validate-jwt: External ID issuer and storefront audience.
    • rate-limit-by-key per user or client IP (from X-Azure-ClientIP), plus quota.
    • CORS allowlist.
    • Strip Server and X-Powered-By headers.
    • Backend mTLS client certificate.
    • Pass traceparent through for distributed tracing.
  • Webhooks: for /webhooks/psp, verify the HMAC signature and the PSP's source IP before forwarding.
  • Logging: gateway logs go to Event Hubs → Splunk. Body logging stays disabled so no PII or tokens end up in logs.

Cross-cluster communication

  • How tiers connect: each cluster exposes an internal Istio ingress gateway behind an internal load balancer IP in its node subnet.
  • NSG rules work by subnet: with CNI Overlay, pod traffic leaving a cluster is SNAT'd to the node IP, so subnet-based NSG rules apply cleanly.
  • Network rules aren't authentication: each call also carries an Entra workload-identity token (client-credentials flow, audience = target API), and the receiving service validates it.

Workload standards

  • Availability: zone-spread topology constraints, PodDisruptionBudgets, readiness/liveness probes.
  • Resources and scaling: CPU/memory requests and limits on every container. Scale with HPA, or KEDA for Service Bus queue depth.
  • Pod security: Azure Policy restricted baseline: no privileged pods, non-root, read-only root filesystem.
  • Network policy: Cilium default-deny in every namespace, with explicit allow rules.
  • Secrets: none in Git or environment manifests. Use the CSI driver or Workload Identity.

Equifax integration

  • Authentication: mTLS client certificate plus OAuth client credentials, both in Key Vault. Track certificate expiry and alert 30 days before.
  • Resilience:
    • 3 s timeout.
    • Retries with jitter, for idempotent calls only.
    • Circuit breaker and bulkhead around the client.
    • When Equifax is down, the order moves to Pending verification and is processed asynchronously. Checkout doesn't fail.
  • Data handling: store only the decision, the reference ID and a timestamp, never the full report. Encrypt identifiers (Always Encrypted) and set a retention period with compliance. TBD
  • Audit: log every inquiry with its permissible purpose and the user/order reference (no PII in the log line).

Payments (PCI scope)

  • Card entry: the browser loads the PSP's hosted payment fields (iframe). The PSP returns a token, so card numbers never touch Front Door, APIM or AKS.
  • Charging: the Middle tier charges the token through the PSP API (egress via the firewall) using an idempotency key per order.
  • Webhooks: PSP events enter at /webhooks/psp (Front Door → App Gateway → APIM signature check) and are processed idempotently.
  • PCI DSS 4.0.1 script controls: the checkout page still needs a script inventory and integrity checks (req. 6.4.3 / 11.6.1). Use Content Security Policy and tamper detection.

Data ownership rules

  • Single owner: only the Data Layer AKS has network and identity access to SQL, Cosmos and Redis.
  • Carts survive cache loss: carts are stored in Cosmos, and Redis only caches them.
  • Catalog vs inventory: catalog content lives in Cosmos, while stock levels live in SQL (strong consistency). Catalog views get stock through events, not dual writes.

  • Terraform runs on agents inside the private network.
  • Flux pulls application changes into the clusters.

Common application delivery flow

  1. PR: build, unit tests, SAST, dependency scanning and secret scanning.
  2. Merge:
    • Build the image and push it to JFrog.
    • Xray scans it; the pipeline fails on critical findings.

D 40 Interview Questions

Q1A customer says "we want to move to Azure." What do you do before migrating anything?
Strategy & planning

Don't start with tools. Start with why, what and when, using the CAF phases.

  • Strategy: business drivers (DC exit, contract renewal, cost, resilience), a hard deadline, an executive sponsor, and measurable success criteria.
  • Plan: discover and assess with Azure Migrate (performance + dependencies), decide the 7 Rs for each app, build the business case and the wave plan.
  • Ready: deploy the landing zone and connectivity to the source before the first workload moves.
  • Migrate: pilot wave first, then repeatable waves with test migrations, cutover runbooks and hypercare.
  • Afterwards: optimize costs and decommission the source, otherwise you pay twice.
Follow-up: "The deadline is 6 months." → Rehost first and modernize later. Build a minimal but policy-driven landing zone. Run waves in parallel using a migration factory.
Q2Explain the 7 Rs. How do you decide which one applies to each application?
Strategy & planning
  • Retire: nobody uses it. Typically 10–20% of an estate.
  • Retain: it can't or shouldn't move yet (mainframe, special hardware, regulatory).
  • Rehost (lift and shift): VM to VM, the fastest option.
  • Replatform: small changes to use PaaS, e.g. SQL Server → Azure SQL Managed Instance, or IIS → App Service.
  • Refactor: code changes for cloud services, e.g. containerize onto AKS.
  • Rearchitect / Rebuild: redesign for cloud-native scale.
  • Replace (repurchase): move to SaaS, e.g. on-prem CRM → Dynamics 365 or Salesforce.

How to decide: plot business value against technical health, constrained by the deadline and team skills.

  • A DC-exit deadline pushes most apps toward rehost.
  • Strategic, high-change apps justify refactoring.
  • End-of-life apps get retired or replaced.
Follow-up: "Why not refactor everything?" → Time, cost and risk. Refactoring during migration doubles the change in a single event. Prefer "migrate, then modernize" unless the app has to be rebuilt anyway.
Q3How do you run discovery and assessment? Which tools, and for how long?
Strategy & planning

Tooling: deploy the Azure Migrate appliance (VMware, Hyper-V or physical; AWS and GCP VMs count as physical). It collects:

  • Configuration, and performance (CPU, memory, disk IOPS and throughput, network).
  • Installed software, SQL instances and web apps.
  • Agentless dependency data.
  • Duration: collect for at least 30 days so month-end and batch peaks are captured. Size on P95 utilization, not on the allocated size.
  • Outputs: Azure readiness, right-sized SKUs, monthly cost, business case. Separate assessments exist for AVS, SQL and App Service.
  • Cloud sources: also use the native inventory (AWS Config / Resource Explorer, GCP Cloud Asset Inventory) and billing exports, which show what is really used and paid for.
  • Non-tool discovery: interview app owners. Collect the CMDB, licences, SLAs, compliance needs, integrations and batch schedules. Tools can't tell you that "this server runs payroll on the 25th".
Q4How do you plan migration waves?
Strategy & planning
  • Move groups: build them from the dependency map. Chatty components (an app plus its database) move together to avoid cross-cloud latency.
  • Wave 0: shared services first (AD/DNS, monitoring, backup, jump hosts).
  • Pilot wave: low-risk, non-production, stateless apps. Proves the process and the runbook.
  • Grow the waves: e.g. 5 → 20 → 50 servers as the team gets faster.
  • Order: critical or complex apps come later, once the factory is proven.
  • Calendar: respect business events (retail peak, quarter-end) and change freezes.
  • Every wave has: an owner, test migration, cutover window, go/no-go, hypercare and a retrospective.
Q5What is a landing zone, and why must it exist before migration?
Strategy & planning

A landing zone is the pre-built, policy-governed foundation that workloads land in.

  • Hierarchy: management groups and subscriptions (platform: identity, management, connectivity; application landing zones).
  • Building blocks: hub-spoke networking, Entra ID + PIM, Azure Policy, central logging, Defender, backup, naming and tagging.
  • Accelerators: the Azure landing zone templates (Terraform / Bicep, Azure Verified Modules).

Why first: without it, every wave invents its own network and security. Retrofitting governance onto hundreds of migrated VMs costs far more than doing it up front. The Readme (§3–§13) is an example of an application landing zone.

Q6How do you build the business case and TCO?
Strategy & planning
  • Starting point: the Azure Migrate business case, which compares current cost (compute, storage, network, facilities, labour) with Azure, right-sized from performance data.
  • Savings levers:
    • Azure Hybrid Benefit for Windows Server and SQL Server licences (and RHEL/SLES).
    • Reservations / savings plans.
    • Extended Security Updates included on Azure for eligible older versions.
    • Autoscaling, and shutting down non-prod.
  • One-time costs to include:
    • Dual-running months.
    • Egress from the source cloud; ask AWS or GCP about their egress waivers for customers leaving.
    • Partner and tooling costs, training.
  • Funding: ask the Microsoft account team about current migration funding or credits programmes.
  • Non-cost value: resilience, security posture, speed of delivery, avoided hardware refresh.
Q7What are the biggest risks in a migration project, and how do you mitigate them?
Strategy & planning
  • Unknown dependencies: dependency analysis, owner interviews, test migrations.
  • Hard-coded IPs and hostnames: config and code scans, DNS aliases, a re-IP plan.
  • Performance differences: pre-migration baseline, load testing in Azure, correct disk tiers.
  • Licensing surprises (Oracle, ISV licences tied to hardware): licence review during assessment.
  • Data loss or long downtime: online replication, validation, rehearsed runbooks, a rollback plan.
  • Skills gap: training, a partner, a platform team.
  • Scope creep (refactoring everything): strict 7R decisions with change control.
  • Cost overrun from dual running: decommission dates are part of every wave.
  • Quota or capacity limits: raise quotas early; use capacity reservations for big cutovers.
Q8How do you govern the programme and measure success?
Strategy & planning
  • Structure: executive steering committee, Cloud Centre of Excellence / platform team, migration factory squads, app-owner sign-off at go/no-go.
  • Artefacts: RACI, risk and issue log, wave tracker, runbooks, decision records.
  • KPIs:
    • Apps migrated against plan; downtime per cutover against the agreed window.
    • Incidents during hypercare; performance against baseline.
    • Cost against business case; % of resources compliant with Policy; Secure Score.
    • Source infrastructure decommissioned on time.
Q9Map the core AWS services to Azure. What differences catch teams out?
AWS → Azure

Use the cheat sheet (section C). The differences that cause real problems:

  • Subnets: AWS subnets belong to one AZ; Azure subnets span all zones. Zone placement happens per resource, not per subnet.
  • Accounts vs subscriptions: an AWS account roughly equals a subscription. Azure adds resource groups and management groups, and SCPs become Azure Policy.
  • Identity: IAM JSON policies on resources become RBAC role assignments at a scope, plus Entra ID for people.
  • Outbound internet: new Azure VNets default to private subnets (no default outbound access). Plan NAT Gateway or Firewall explicitly.
  • Load balancers: ALB → Application Gateway (regional L7), NLB → Load Balancer (L4). CloudFront + WAF → Front Door.
  • S3 API: Blob Storage doesn't speak the S3 API. Apps need SDK changes.
Q10How do you migrate EC2 workloads to Azure?
AWS → Azure

Pets (unique, stateful servers) → rehost with Azure Migrate, treating EC2 instances as physical servers:

  • Discover with the appliance, then install the Mobility agent and replicate through a replication appliance.
  • Run a test migration into an isolated VNet, then migrate.
  • Afterwards, remove AWS agents (SSM, CloudWatch), install the Azure VM agent, and check that Linux has the Hyper-V drivers in initramfs.

Cattle (auto-scaled, stateless) → don't copy instances; rebuild:

  • Bake images with Packer into Azure Compute Gallery.
  • Deploy VM Scale Sets with Terraform.
Watch out: Graviton (ARM) instances need Arm64 images on Azure (Arm-based VM sizes) or a rebuild for x64. Check every instance's architecture.
Q11How would you migrate an EKS platform to AKS?
AWS → Azure

You don't lift a cluster. You rebuild AKS with IaC and redeploy workloads with GitOps, then shift traffic gradually. Translate each integration point:

  • IRSA / EKS Pod Identity → Entra Workload Identity (§12)
  • ECR → ACR (az acr import or oras cp)
  • AWS Load Balancer Controller → App Gateway for Containers / Istio ingress. Service annotations change from aws-load-balancer-* to azure-load-balancer-*.
  • EBS CSI → Azure Disk CSI; EFS → Azure Files CSI
  • Secrets Manager → Key Vault (CSI driver or External Secrets)
  • Karpenter → AKS Node Auto-Provisioning; Cluster Autoscaler is equivalent
  • CloudWatch Container Insights → Azure Monitor (§14)

State and traffic:

  • Persistent-volume data moves with Velero, or better, with application-level replication.
  • Run both platforms side by side and shift traffic with weighted DNS (Route 53 or Front Door), then cut over.
Q12You need to move 500 TB from S3 to Azure. How?
AWS → Azure
  • Inventory first: buckets, object counts, versioning, lifecycle rules, encryption, bucket policies, event notifications. Map each bucket to a storage account and container.
  • Copy:
    • AzCopy supports S3 as a source and copies server-to-server, so data doesn't pass through your machine.
    • For scheduling, retries and incremental copies (by LastModified), use Azure Data Factory.
    • Data Box isn't for cloud-to-cloud.
  • Pattern: bulk copy → incremental syncs → freeze writes → final delta → switch apps → validate (counts, sizes, checksums).
  • Cost: S3 egress at this volume is tens of thousands of dollars. Ask AWS about the migration egress waiver, and budget for it if it isn't granted.
  • App changes: code using the S3 SDK must move to the Blob SDK.
Q13How do you translate AWS IAM and Organizations to Azure?
AWS → Azure
  • Hierarchy: Organization / OUs / accounts → Entra tenant / management groups / subscriptions.
  • Guardrails: SCPs → Azure Policy (deny) at management-group scope.
  • People: IAM users → Entra users (no local users). Human IAM roles → Entra groups + PIM-eligible RBAC roles.
  • Workloads: instance profiles / IRSA → managed identities / Workload Identity.
  • Policies: IAM policies → built-in or custom RBAC roles at the narrowest scope, plus ABAC conditions. Permission boundaries have no direct equivalent; combine custom roles, Policy and PIM.
  • Audit: CloudTrail → Activity Log + Entra audit logs.
Tip: federate AWS to Entra ID early, so one identity covers both clouds during the transition.
Q14How do you connect AWS and Azure during the migration?
AWS → Azure
  • Standard option: site-to-site IPsec VPN with BGP between an AWS Transit Gateway / VGW and an active-active Azure VPN Gateway. Each AWS tunnel tops out around 1.25 Gbps; use several tunnels with ECMP for more.
  • High throughput: Direct Connect + ExpressRoute meeting at a colocation or partner fabric (e.g. Equinix, Megaport).
  • Prerequisite: non-overlapping CIDRs.
  • Hybrid DNS in both directions: Route 53 Resolver endpoints ↔ Azure DNS Private Resolver.
  • Security: firewall on both sides; only the flows the migration actually needs.
  • Design rule: keep cross-cloud chatty calls to a minimum. Move dependent apps together.
Q15What are the key GCP-to-Azure differences an architect must plan for?
GCP → Azure
  • Networking: a GCP VPC is global with regional subnets. An Azure VNet is regional, so a multi-region design needs a VNet per region plus peering or Virtual WAN.
  • Projects: GCP projects are very granular. Map groups of projects to subscriptions, and smaller projects to resource groups.
  • Hierarchy and identity:
    • Folders → management groups.
    • Org policies → Azure Policy.
    • Service accounts → managed identities.
    • IAM bindings → RBAC assignments.
  • Global load balancing: the single global Cloud Load Balancer splits into Front Door (global) + Application Gateway (regional).
  • Analytics is often the biggest workstream: BigQuery / Dataflow / Dataproc / Looker → Fabric / Databricks / Power BI.
  • Connectivity: HA VPN ↔ Azure VPN Gateway, or Cross-Cloud Interconnect.
Q16Migrate an app running on GKE with Cloud SQL (PostgreSQL) and Memorystore to Azure.
GCP → Azure
  • Ready: landing zone, VPN/Interconnect to GCP, AKS built with IaC.
  • Database: Cloud SQL → Azure Database for PostgreSQL Flexible Server using the built-in migration service in online mode (logical replication). Enable logical decoding on Cloud SQL first.
  • Platform pieces:
    • Artifact Registry → ACR.
    • GKE Workload Identity → Entra Workload Identity.
    • Secret Manager → Key Vault.
    • Memorystore → Azure Managed Redis (warm the cache; don't migrate it).
    • Cloud Armor + Load Balancer → Front Door + WAF.
  • Deploy: GitOps (Flux) deploys the same manifests with Azure overlays.
  • Cutover: replication lag reaches 0 → stop writes → promote Azure → switch the connection string (Key Vault) → move DNS (Cloud DNS → Azure DNS) → smoke tests.
Q17How would you migrate BigQuery analytics to Azure?
GCP → Azure
  • Assess: datasets, sizes, scheduled queries, UDFs, BI dependencies, and the cost model. BigQuery bills slots or bytes scanned; Fabric bills capacity units.
  • Target: Microsoft Fabric (Lakehouse / Warehouse on OneLake), or Azure Databricks for Spark-heavy teams. Looker → Power BI.
  • Data: export tables to GCS as Parquet. Then either use OneLake shortcuts to GCS for a quick start, or copy them in (Fabric Data Factory / AzCopy).
  • Code: convert the SQL dialect (BigQuery SQL → T-SQL / Spark SQL) and rebuild pipelines (Dataflow → Fabric pipelines / Databricks).
  • Prove it: run both in parallel, reconcile key reports, then switch consumers.
Q18What do Pub/Sub, Cloud Run and Cloud Functions become on Azure?
GCP → Azure

Pub/Sub splits into three services depending on the use case:

  • Service Bus: commands or transactional messages that need DLQ, sessions and ordering.
  • Event Hubs: high-throughput streaming (Kafka-compatible).
  • Event Grid: push-style event notifications.

Compute and scheduling:

  • Cloud Run → Container Apps: same container, scale-to-zero, KEDA-based scaling.
  • Cloud Functions → Azure Functions. Use the Flex Consumption plan for VNet integration.
  • Cloud Scheduler / Cloud Tasks → Functions timer triggers / Logic Apps / Service Bus scheduled messages.
Point to make: the semantics differ (delivery guarantees, ordering, retries). Test idempotency rather than assuming a 1:1 port.
Q19The customer has 2,000 VMware VMs and must leave the data centre in 9 months. What do you recommend?
On-prem / bare metal

There are two paths, and they're often combined.

Azure VMware Solution (AVS) + HCX

  • Fastest: same vSphere tools, often no re-IP thanks to L2 extension, almost no app change.
  • Good for hitting the DC-exit date.
  • Costs: dedicated hosts and VMware licensing terms. Check the current licensing model.

Azure Migrate → native Azure VMs (agentless VMware replication)

  • Cheaper over time and uses native PaaS and monitoring.
  • Needs re-IP, and staff to operate Azure-native.

Typical answer: move the bulk to AVS to meet the deadline, take strategic apps native, then modernize out of AVS over 12–24 months.

Q20How do you migrate physical / bare-metal servers? What can't move?
On-prem / bare metal
  • Process: discover with the Azure Migrate appliance (physical), replicate with the agent-based Mobility service, test migration, cutover. Check the OS support matrix first.
  • Blockers:
    • Special hardware: dongles, PCIe cards, specific GPUs, HBAs.
    • Licences bound to MAC address or hardware ID.
    • Very old OSes (upgrade or rebuild first).
    • Multicast/broadcast: not supported in Azure VNets.
    • Shared-disk clusters (redesign, or use Azure shared disks).
    • Ultra-low-latency workloads; mainframe, AS/400 or SPARC (partner rehost, emulation or rewrite).
  • Options for blockers: retain them, use Azure Dedicated Host for licensing or isolation, or manage the leftovers with Azure Arc.
Q21How does licensing affect a Windows / SQL Server migration?
On-prem / bare metal
  • Azure Hybrid Benefit: reuse Windows Server and SQL Server licences with Software Assurance. This saves a large share of the compute cost. RHEL and SLES have a similar BYOS model.
  • Extended Security Updates: free on Azure for eligible end-of-support versions. Check current end dates (Windows Server 2012/R2 ESUs ran to October 2026, so those servers now need upgrade or rebuild).
  • Oracle: on Azure, Oracle's authorised-cloud policy counts vCPUs differently from on-prem cores. Model the cost before you choose VM sizes.
  • ISV licences: confirm that cloud deployment is allowed, and whether the licence is tied to hardware.
Q22How do you manage servers that are half-migrated, or that stay on-prem?
On-prem / bare metal

Azure Arc brings on-prem, AWS and GCP servers, Kubernetes clusters and SQL instances into Azure Resource Manager. That gives you a single control plane:

  • Azure Policy, Defender for Cloud, Update Manager.
  • Azure Monitor, RBAC and tags.

When it helps:

  • During migration it standardizes operations and security before the move.
  • For workloads you retain, it becomes the permanent hybrid management model.
Q23When would you use Azure Data Box instead of the network?
On-prem / bare metal

Do the bandwidth maths out loud:

  • 1 Gbps moves about 10 TB/day at full saturation, or about 7–8 TB/day realistically.
  • So 500 TB takes roughly 60–70 days, and production traffic shares that link.

Recommendation:

  • For large initial seeds with a limited link, use Data Box (offline, encrypted, shipped). Then catch up online with AzCopy / Storage Mover deltas.
  • For small volumes or continuous change, use the network (Storage Mover, AzCopy, replication).
Q24How do you handle Active Directory and identity in an on-prem migration?
On-prem / bare metal
  • Keep AD DS authoritative at first. Sync to Entra ID with Entra Connect Sync or Cloud Sync (password hash sync recommended), enable SSO, and turn on Conditional Access and MFA.
  • Domain controllers in Azure: put DCs on VMs in the identity subscription, as their own AD site, so migrated legacy apps still get local Kerberos/LDAP. Microsoft Entra Domain Services can suit simple cases.
  • Modernize over time: move apps to OIDC/SAML on Entra ID, and replace service accounts with managed identities.
  • From AWS: AWS Managed Microsoft AD → AD DS on Azure VMs or Entra Domain Services.
Q25Online vs offline database migration: how do you keep downtime to a minimum?
Data & databases

Offline vs online:

  • Offline (backup/restore, dump/load): downtime equals the full copy and restore time. Simple, and fine for small databases or generous windows.
  • Online (initial load + change data capture): downtime is just the final lag plus the app switch, usually minutes.

Online tools:

  • DMS (SQL Server, MySQL).
  • Managed Instance link.
  • The PostgreSQL migration service (logical replication).
  • Native replication (MySQL binlog, PostgreSQL logical replication).

Gotchas:

  • Tables without primary keys (logical replication needs them).
  • Large objects (LOBs).
  • Sequences and identity values.
  • Triggers and jobs on the target (disable until cutover).
  • Collation and time zones.
Q26SQL Server: Azure SQL Database, Managed Instance, or SQL on a VM? How do you choose?
Data & databases
  • Azure SQL Database: fully managed per-database PaaS for modern apps. No instance-level features (SQL Agent, cross-database queries, CLR are limited).
  • Managed Instance: near-full instance compatibility (SQL Agent, cross-database queries, linked servers, Service Broker). The best lift-and-shift PaaS target. MI link gives near-zero-downtime migration, with failback possible to SQL Server 2022.
  • SQL Server on a VM: you need OS access, unsupported features, specific versions, or third-party agents. Most control, most operations work.

How to decide: run the Azure Migrate SQL assessment, which flags blockers and recommends a target and SKU.

Q27How do you handle Oracle databases in an Azure migration?
Data & databases
  • Oracle Database@Azure: Exadata / Autonomous Database running in Azure data centres, operated by Oracle. Lowest change for RAC and Exadata workloads; Oracle's Zero Downtime Migration tooling supports the move.
  • Oracle on Azure VMs: works for single instances with Data Guard for HA. RAC isn't supported on plain VMs. Watch the licence cost of vCPUs.
  • Refactor to Azure Database for PostgreSQL: removes Oracle licences. Needs schema and PL/SQL conversion (e.g. ora2pg) and app testing, so it's a project in its own right.

Decision factors: licence position, use of RAC or Exadata features, the PL/SQL footprint, and the timeline.

Q28How do you migrate DynamoDB, Firestore or MongoDB to Cosmos DB?
Data & databases
  • Data model: design the partition key first.
    • DynamoDB partition key ≈ Cosmos partition key; the sort key goes into id or a composite key.
    • Alternate access patterns (GSIs) may need change-feed-built views.
    • Cosmos indexes every property by default.
  • Throughput: RCU/WCU → RU/s (about 1 RU per 1 KB point read). Choose autoscale or serverless.
  • Features: choose a consistency level (Session is the default). Streams → change feed. Transactions → transactional batch within one partition.
  • Moving the data:
    • DynamoDB: export to S3 → ADF / Spark bulk load. For online cutover, replay changes from DynamoDB Streams.
    • MongoDB → Cosmos DB for MongoDB (vCore), using DMS online migration.
Q29How do you prove data was migrated correctly?
Data & databases
  • Before cutover: replication lag at 0 and writes frozen.
  • Structural checks: schema, objects, indexes, constraints, users and permissions compared.
  • Data checks: row counts per table, checksums or hashes per table or partition, min/max on key columns.
  • Business checks: the same report or query run on source and target (order totals, account balances) must match exactly.
  • Application checks: smoke tests and UAT scripts signed off by the app owner.
  • Evidence: keep it in the cutover record. Auditors and the go/no-go call both need it.
Q30What goes into a cutover runbook?
Cutover & rollback
  • Who: scope, owners (RACI), contact list, communication plan.
  • Go/no-go criteria and who makes the decision.
  • Pre-checks:
    • Replication healthy; backups taken.
    • DNS TTL lowered 48–72 h before.
    • Certificates, firewall rules and quotas in place; monitoring live.
  • Minute-by-minute steps: maintenance page → stop writes and jobs → final sync → validate data → switch config / connection strings → DNS change → smoke tests → open traffic.
  • Rollback: triggers, a time box ("not validated by T+2h → roll back") and the point of no return.
  • After cutover: hypercare rota and success sign-off.
  • Rehearse it in a dress rehearsal and record the timings.
Q31How do you test before a production cutover?
Cutover & rollback
  • Test migration: Azure Migrate test migrations bring up replicas in an isolated VNet with no production impact.
  • Functional: functional tests and UAT by app owners; check integrations against test endpoints.
  • Performance: load test in Azure compared with the pre-migration baseline.
  • Security: vulnerability scan, Policy compliance, penetration test for internet-facing apps.
  • Operations: backup restore test, DR failover test, and checks that alerts actually fire.
  • Dress rehearsal of the runbook, to measure the real downtime.
Q32What's your rollback strategy?
Cutover & rollback
  • Keep the source intact (read-only, not deleted) until the rollback window closes, typically 1–4 weeks.
  • Before the point of no return: repoint DNS / config to the source; data is unchanged.
  • After new writes land in Azure: you need reverse replication (e.g. MI link failback, or reverse logical replication) or a documented data reconciliation.
  • Governance: pre-agreed triggers (error rate, latency, failed validation), one named decision owner, and a rollback that has been tested.
Q33How do you handle DNS, certificates and hard-coded IPs at cutover?
Cutover & rollback
  • Inventory: every hostname, DNS record and certificate (expiry, issuer, where it's installed).
  • DNS: lower TTLs to 60–300 s a few days ahead; switch records at cutover; restore TTLs afterwards. Use hybrid resolution (DNS Private Resolver) during coexistence.
  • Certificates: import or reissue them into Key Vault; update SANs for new endpoints.
  • Hard-coded IPs: find them with dependency analysis plus config and code scans. Replace them with DNS names, or keep the IPs where possible (static IP at the target; HCX L2 extension on AVS).
Q34Walk me through the request flow of a secure, multi-tier e-commerce app on Azure.
Azure architecture
  1. Front Door Premium with WAF.
  2. Private Link to a private App Gateway.
  3. Pages go to the Frontend AKS cluster; /api goes to internal APIM (JWT validation).
  4. Frontend → Middle → Data AKS over TLS, each call carrying a workload-identity token.
  5. Data stores are reached through Private Endpoints.
  6. Outbound calls (Equifax, payment provider) leave through Azure Firewall.

Explain why for each hop: Front Door can't reach APIM in internal mode directly; WAF at the edge; no public data endpoints; one inspected exit with static IPs. See Readme §5.

Q35Private Endpoint vs Service Endpoint: which do you use, and what about DNS?
Azure architecture
  • Service Endpoint: the service keeps its public IP, but traffic from the subnet travels over the Azure backbone and the service firewall allows that subnet. Not reachable from on-prem or peered networks; weaker against data exfiltration.
  • Private Endpoint: a private IP in your VNet for one specific resource. Works from peered VNets and on-prem, and public access can be disabled completely. This is the standard for enterprise and regulated workloads.
  • DNS is the hard part: you need a privatelink.* private DNS zone linked to the VNets, with automatic registration via Policy, and a DNS Private Resolver for on-prem. See Readme §4.
Q36Why hub-and-spoke with Azure Firewall rather than just a NAT Gateway?
Azure architecture
  • NAT Gateway: only provides outbound SNAT and static IPs. No filtering, no logging of destinations, no IDPS.
  • Azure Firewall in the hub:
    • FQDN allowlists, threat intelligence and IDPS.
    • Central logging; a DNS proxy.
    • One policy shared by all spokes.
  • Using both: attach a NAT Gateway to the firewall subnet for SNAT port scale and fixed egress IPs.
  • Hub-spoke benefits: shared connectivity (ExpressRoute/VPN), shared DNS, isolation between spokes. Virtual WAN is the managed alternative at scale.
Q37How do workloads reach databases without passwords?
Azure architecture

Managed identities. On AKS this means Workload Identity:

  • The cluster OIDC issuer signs a Kubernetes service-account token.
  • A federated credential on a user-assigned identity trusts that service account.
  • The pod exchanges the token with Entra ID for an access token, which SQL, Cosmos, Service Bus and Key Vault accept.

Finish the job: disable local/key authentication on the services and grant least-privilege data roles.

Same idea as AWS IRSA or GKE Workload Identity, which is a useful comparison when the interviewer comes from another cloud.

Q38How do you design for high availability and disaster recovery?
Azure architecture
  • HA within a region: availability zones for every tier (zone-redundant PaaS, AKS pools spread across zones).
  • DR across regions: chosen per RTO/RPO. Options: backup/restore, pilot light, warm standby, or active-active.
  • Data replication: SQL failover groups, Cosmos multi-region, Service Bus geo-replication, GZRS storage. Front Door switches traffic between origins.
  • Composite SLA: multiply the SLAs of components in series. A long chain falls below the target unless you add a second region.
  • Practice: test it. Chaos experiments and scheduled failover drills, plus documented runbooks.

See Readme §15.

Q39What happens after the workloads are migrated?
Post-migration
  • Hypercare (2–4 weeks): heightened monitoring, quick fixes, hand-over to operations with runbooks.
  • Optimize:
    • Right-size using Advisor and real usage.
    • Buy reservations / savings plans after 30–60 days of stable usage.
    • Autoscaling, non-prod schedules, storage tiering.
  • FinOps: tags for chargeback, budgets and anomaly alerts, a monthly cost review.
  • Decommission the source after the rollback window: archive data per retention, delete resources, end DC/hosting/licence contracts, update the CMDB. This is where the business case is realised.
  • Modernize: the next roadmap, e.g. VM → PaaS / containers.
Q40Scenario: after migration the app is slower in Azure than it was in AWS / on-prem. How do you troubleshoot?
Post-migration
  1. Compare with the baseline: which transactions are slower, and since when? Use Application Insights or Datadog traces to find the slow hop.
  2. Cross-cloud calls: is the app still calling a database or service left in the source? Hundreds of calls × 20–40 ms each is the most common cause.
  3. Placement: right region? Are VMs and the database in the same region and zone? Is accelerated networking on? Proximity placement groups for latency-sensitive tiers.
  4. Sizing and disks: disk tier and IOPS/throughput caps (Premium SSD v2 / Ultra), host caching, VM size limits, database tier/DTU or vCore throttling.
  5. Network path: SNAT port exhaustion on outbound, firewall TLS-inspection latency, DNS resolution going on-prem and back.
  6. Fix, measure, compare again.

E How to Answer & What to Ask Them

Answering tips

  • Structure: context → options → decision → trade-off → how you'd validate it.
  • Always say why, and name the alternative you rejected.
  • Use numbers: TB, Gbps, RTO/RPO, server counts, weeks.
  • For "tell me about a time…" questions, use STAR (Situation, Task, Action, Result) and include something that went wrong and what you changed.
  • Be honest about your experience. "I designed it this way and here's why" is strong. Don't claim production experience you don't have.
  • If you don't know a detail, say how you'd find out (docs, assessment tool, PoC).

Questions to ask the interviewer

  • What's driving the migration, and is there a hard deadline?
  • What's the source mix (AWS, GCP, VMware, physical), and roughly how many workloads?
  • Is the landing zone already built, or part of this project?
  • What's the target mix of rehost vs modernize?
  • Which compliance regimes apply (PCI, HIPAA, SOC 2, data residency)?
  • Is a partner involved, and how is the team split (platform, migration factory, app teams)?
  • How is success measured for this role in the first 6 months?
